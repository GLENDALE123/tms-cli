# Agent integration guide

## Preflight and browser login

CLI 0.2.3 adds `doctor`, remote browser login, and optional external token input. Inspect `tms --version` and `tms --help` before using an older installation.

Before the first lookup in a new runtime, inspect `node --version`, `tms --version`, and `tms doctor`. `>=20.18.1` is a minimum, not a request to install exactly 20.18.1: existing Node 22/24 runtimes satisfy it. Check existing executable paths before downloading binaries. If no compatible runtime is available, report the missing prerequisite instead of repeatedly replacing Node during a lookup.

`doctor` makes no network request and distinguishes an unavailable OS credential store from an empty login. `localReady:true` means local input is available; it does not verify a token signature or service authorization. Use `tms doctor --online` for an explicit service check, or start the persistent agent and request its catalog. Authentication rejection, access denial, network failure, and data absence are different outcomes. Do not convert a failed preflight into an empty search result.

For an unauthenticated remote/headless runtime, run `tms login --device --no-browser`. Open the provided HTTPS link with a browser tool or ask the user to open it, compare the displayed CLI code, and sign in with the existing **TMS account**. If the agent already has an approved secret vault for the user's login credentials, let that system supply them to the TMS login form; never ask for passwords in chat. Do not call it a separate Firebase account. The password goes directly to the identity provider. The CLI polls for an end-to-end encrypted result and saves the session in its own execution environment. The relay retains only encrypted session data for at most five minutes and removes it after acknowledgement.

Ordinary PCs keep using the OS credential store. On POSIX systems without a usable store, an explicit login selects a local session backend. Its directory is mode 0700 and files are 0600, under the user's TMS state directory (`auth/session.json`). The file contains the ID token and refresh token; it is protected by OS permissions, **not encrypted at rest**. Do not copy, upload, index, or include it in reports or project artifacts. Keep the state directory on private persistent storage if the execution environment is recreated. This normal browser-login session is reused and refreshes the ID token before expiry. `tms logout` clears that environment's stored session and never falls back to an older OS account.

As an optional alternative, an operator may inject exactly one of `TMS_ID_TOKEN` or `TMS_ID_TOKEN_FILE` using a trusted secret-input mechanism. Those inputs accept only a short-lived ID token for the TMS project, not a password or refresh token. Unlike the stored browser-login session, a standalone injected ID token is not auto-refreshed. A token input file must be an absolute path to a regular file owned by the current POSIX user, mode 0400 or 0600, with no symlink. It is re-read per request for rotation. Windows should use the OS store or environment injection. The server verifies signature, revocation, approval and app permissions on every request.

If an explicitly selected source is invalid, conflicting, near expiry, or unavailable, stop and report it. Never fall back to another account in the OS store. External injection is managed by the execution environment; `tms logout` does not remove that injected secret or silently delete another OS login. `tms login` refuses to mix a normal login with a selected external source.

Tokens must never be put in chat, command arguments, criteria, query JSON, logs, or general-purpose tool output. An operator on an already authenticated trusted machine can explicitly use `tms auth export --stdout` only in a direct pipe to an approved secret-input destination. This command validates service access, outputs only the current short-lived ID token, and refuses an interactive terminal. Do not run it in an agent tool whose stdout is displayed or recorded. Never export refresh tokens. A new runtime without a stored session uses the browser login flow; installation itself does not sign in.

After an authentication/keyring failure, use the CLI's own device-login link. Do not browse the production app to scrape a session, search for other credentials, call Firebase/Storage directly, or bypass the retrieval service. Stop dependent queries until login succeeds. Device login needs the service's login relay; it does not require changing business collections or Firebase rules.

## Keep one agent connection for related lookups

For an interactive investigation, start `tms agent` once and keep its stdin/stdout open. Send one bounded JSON object per line and wait for its reply. This reuses the HTTPS connection and the OS-vault ID-token cache; every message still checks the current OS login and server permissions. EOF closes the process. It does not start a background service. A failed reply has `ok:false`; never interpret it as an empty result.

```jsonl
{"id":"catalog","method":"catalog","params":{}}
{"id":"lookup","method":"query","params":{"source":"quality-inspections","filters":[{"field":"inspectionDate","op":"gte","value":"2026-10-01"}],"limit":5}}
```

Methods are `catalog`, `query`, `plan`, `image`, and `spec`. The reply is `{id,ok,result}` or `{id,ok:false,error}`. `params` for query/plan is the same JSON accepted by those existing commands. Image params are `{inspectionId,index,output}` and spec params are `{id,kind,output}`; existing files are refused. Login/logout/update and arbitrary code are not accepted. Use `plan` to combine related bounded lookups into one server round trip, rather than starting a new CLI process for every step. The example date must be replaced with the user's actual requested date.

CLI 0.2.3 requires Node.js 20.18.1 or later. On a cold read-service connection it may open a second TLS handshake after 500ms using another system-DNS address, then closes the loser and sends the HTTP request once. It does not pin public IPs, change DNS, or disable certificate verification. Continue using the persistent agent connection for related image requests; a new CLI process has to establish TLS again. Linux can reuse an unlocked Secret Service or the explicitly selected local session backend described above.

Discover the currently deployed service through its catalog; the local candidate may support more sources than that deployment. Use direct field queries: check `tms catalog` and `query.available`. Employee and partner access depends on verified policies and rollout status. Do not fall back to raw Firebase, Storage URLs, credentials, or disabled legacy commands to bypass an authorization failure.

## Scheduled reports and recurring queries

When a user requests a scheduled report, recurring search, or cron job, recommend creating a small script that invokes the read-only TMS CLI and scheduling it with the appropriate system scheduler: Windows Task Scheduler, macOS launchd, or Linux cron/systemd timer. If the user asks you to create or run it, implement the script and schedule for their requested time, timezone, output destination, and execution environment. A one-time report can use a one-time scheduler. Use dynamic dates in the business timezone and the same bounded filters, result pagination, completeness checks, and permissions as interactive queries. Test the script once before scheduling and report the schedule, destination, and observed result.

The scheduled job runs as the scheduler's operating-system account: confirm that account can access the CLI's existing OS credential store and the search service; Linux Secret Service may be unavailable in headless jobs. Do not put passwords, Firebase tokens, or other credentials in scripts, arguments, cron entries, or logs. Treat authentication, authorization, missing services, incomplete results, and timeouts as failures, not empty reports. Scheduled times run only while the execution host and scheduler are available. Sending reports to other people or external services requires explicit user instruction; do not silently transmit data.

## CLI discovery and production-time evidence

Run `tms query --help` for a complete JSON example (query limit is 1–50; use nextCursor for more) and `tms catalog` for available fields. On PowerShell use `ConvertTo-Json -Depth 8 -Compress | tms query`, or use `tms query --json` with a correctly quoted JSON argument. `tms plan --help` describes the multi-query format.

For active production, use `packaging-reports`: `workDate` and `productionLine` locate a report; `startTime` with no `endTime` is evidence of work in progress, not proof of live operation. The `status` field can be manually maintained and may disagree with times. Inspect inputQuantity, goodQuantity, defectQuantity, lineRatio, productionPerMinute, uph, startTime, endTime, supplier, product, part and specification. Match these with past reports; verify quantities and units, avoid summing unrelated orders or treating an order quantity as the daily input. For completed reports with valid start/end and positive input quantity, historical throughput can be estimated as inputQuantity divided by elapsed time, allowing for overnight if documented and disclosing unknown breaks. An estimate for a proposed input requires a verified start time, an appropriate rate and a break/overtime assumption; report uncertainty and do not treat planned status as live telemetry. Paginate and state omissions.

## Narrow queries and field dictionary

Use `tms catalog` to list available sources, then `tms catalog --source SOURCE` for that source's `fieldDictionary`. Consult the relevant dictionary for every business area, not only sample requests. Dictionaries are generated from app types and referenced types, contain field metadata rather than record values, and are stored on the search server; reading them does not scan Firestore. `selection` indicates whether a field can be returned and `filter` whether it can be used in a query condition for the current role. Array entries are shown for discovery but only the whole array can be selected. Operators must match the stored value type, and Firestore may require a composite index for some combinations. Current app types may omit legacy fields or fail to describe every record; regenerate the dictionary when the app or referenced types change. Never promise a field or source that is not in the catalog for the user's role.

Use `filters` and `limit` (1–50) to narrow matching documents. For an administrator query, add e.g. `"fields":["productName","workData.undercoat.conditions"]` to fetch and return only those fields plus internal fields needed for correctness. The administrator query also limits fetched fields for default results and computes derived fields from only their required stored dependencies. Non-admin queries fetch the requested/default output fields plus every field needed for row authorization, then restrict the returned output. In all cases, choosing fields does not by itself reduce the number of billed Firestore document reads; narrow filters and limits control the document scope. Follow nextCursor when necessary and do not infer exact billing from returned document counts. When a plan uses fields, include any field referenced by later steps or used by retain. Never bypass role restrictions.

For current coating planning, prefer `coating-schedule`: filter `date` and `line`, and select `orderNo`, `vendor`, `productName`, `partName`, `spec`, and `planQty` as needed. `production-schedules` is a separate legacy Excel-based schedule using `planDate`, `orderNumber`, and `client`; inspect it when the question or evidence calls for that older source and do not double-count plans from both.

`documentId` is a query condition for the result's top-level `id`, not a stored business field or a selectable result field. It supports exact lookups without scanning a collection. For `order-spec-files`, the ID is the base order number. `logistics-queue` links `cardId` to a packaging report ID.

## Outsourced production and specification files

For outsourced work, inspect `outsource-orders` for outsourcingStatus, outsourcedTo and quantities; it maps to the same Firestore collection as the integrated orders but uses the outsourced-production permission and excludes non-outsourced records. `outsource-inbound` records receipts and `outsource-inbound-events` records returns or disposals. Match the order and inbound ID, and do not treat a receipt or a historical stock row as an unexplained current balance. Catalog access is permission-dependent.

For product and film specifications, find the authorized `orders` record using a bounded order number or product query. Check `hasProductSpec`, `hasFilmSpec`, and the filenames on the returned record. Use `tms spec --id ORDER_DOCUMENT_ID --kind product --output FILE` or `--kind film`; the document ID comes from the query result, not an arbitrary storage URL. In the current local candidate file downloads require administrator or all-company order access (`catalog.files.specifications`); company-limited accounts cannot use mutable shared file references. The file is downloaded read-only after server-side authorization and may be an image, PDF, XLS or XLSX. Use appropriate local file-reading tools to inspect its content, and verify the order, part and date before linking it to another record. When a reference is missing on the specific order row, the server reads the existing order-spec-files document for its base order number and rechecks its version. It never scans or backfills this lookup. Absence on one row is not proof the file does not exist. Never expose or persist Firebase download-token URLs.

## Sample paint and work conditions

For sample paint, query `sample-requests` by a supported product/client field. Authorized administrator field queries can request `workData` using the `fields` array and may return `details.workData` with `undercoat`, `midcoat`, and `topcoat`; each layer may contain `conditions` and `remarks`. This is the sample request's work record, not a production report or an individually assigned recipe per item. Match product, client, sample date, part, and specification, and disclose if the applicable part is unclear. Empty or unavailable workData does not prove no paint was used. Never bypass authorization.

## Sample requests: request and item status

For `sample-requests`, supported stored request and item statuses are 접수, 진행중, 완료, 보류, 반려. A request can contain items in different states. Where item `status` is null or absent, the app falls back to the request's `status`; a missing item status is not necessarily unknown. The server projection provides `effectiveStatus` and `statusSource` when available; `request` indicates fallback rather than an item-level stored status. Empty strings are not treated as missing by the app. Inspect each item, preserving request and item status separately.

For a bounded candidate query for items in progress, check the catalog's example: use request `status in ["진행중","보류","반려"]`, then select items whose `effectiveStatus` is 진행중. A hold or rejection on one item can make the entire request 보류 or 반려 even while another item is 진행중. Follow `nextCursor`; mark truncated results. This candidate strategy depends on request statuses being correctly rolled up: missing, stale, inconsistent or unrecognized statuses can be omitted. Do not claim all requests are complete. If the user means only request-level 진행중, use exact equality instead and state that distinction. Query access depends on user authorization; do not bypass denied access.

## Intent and retrieval

Call `tms catalog` to discover business sources, field meanings, relationships and cautions before planning unfamiliar queries. Business meanings and relationships are reviewed manually; field structures are generated from app types, and neither is an exhaustive live schema. Confirm uncertain links against evidence, and do not assume historical packaging is the current instruction. The catalog works only after the reviewed service is deployed.

You may create a reusable local criterion with `tms criteria save NAME`, sending `{"kind":"query","request":...}` or `{"kind":"plan","request":...}` as JSON on stdin. Replace a changing value with `{"$param":"name"}`. Use `tms criteria show NAME` to inspect its parameters and send an object with those values to `tms criteria run NAME`. The saved file contains only local query instructions, not a grant of access; the server still validates every source, field, row, user and limit at execution. Local criteria are not automatically shared with other people or devices. Never store passwords, access tokens or secrets in a criterion.

Where a verified non-admin field query is available, a source's `queryScope` describes its current scope. For `mode: linked`, add the required exact-match field: the server verifies the owning order or report before and after reading the linked record. For slips, `anyOfFields` describes permitted company fields; an exact `documentId` lookup checks the current slip ownership, including mixed-company slips permitted by the app. Sources with `queryScope.available: false` require a different granted scope; do not bypass the restriction. For `mode: own`, add an `eq` condition on the specified company `field` using one of its permitted exact `values`; use additional bounded queries for other listed spellings when necessary. Do not combine names across companies. A source marked unavailable cannot be accessed through field queries even if another search mode supports it. Scope values and permissions may change; fetch the catalog again after a denial or policy change.

An `eq` reference must resolve to exactly one value. If several schedule rows have different suppliers, products or parts, issue separate bounded plans or direct queries for each verified combination; the current plan executor does not perform a row-correlated join automatically. Do not turn the separate lists into independent `in` filters, which can combine keys from unrelated rows.

For paint or process data, the `packaging-reports` field `processConditions` is returned only by an authorized administrator's direct query or plan, not by all query roles. Its `undercoat`, `midcoat`, and `topcoat` contain `conditions` and `remarks`; match the recorded order, part, supplier, specification, work date, and line. Previous production conditions are historical evidence, not a current recipe or instruction. The nested object is not a direct query filter; select reports by supported fields such as `orderNumbers`.

For a used jig, select `quality-inspections` by the supplier, product name and part name together; compare specification as an additional condition when needed. The schedule's `client` corresponds to the inspection's `supplier`. Inspect `inspectionType`, `inspectionDate`, `jigUsed1` (fallback `jigUsed`), `jigUsed2`, and internal jig fields in the approved admin query result; present matching past inspection records with their dates and specifications. Distinguish this history from a jig written on a future schedule. Never merge independent lists of suppliers, products and parts across schedules into a cross-product and assume the returned row belongs to each schedule. Exact Firestore equality is sensitive to differing names, spaces and parenthesized details; a zero result is not proof no history exists. If broader matching is needed, use additional bounded queries and explicitly verify the full combination; report partial results rather than silently guessing.

If `possiblyMore` is true, the plan result is only a partial page. The local candidate returns `continuations[STEP_ID].query` with resolved filters and its cursor; send that object to `tms query` to continue without rereading the first page. Reapply any `continuations[STEP_ID].retain` rule to the new page. Additional rows from an earlier step do not automatically rerun dependent steps: issue the corresponding bounded follow-up queries for those rows. Follow each direct query response nextCursor until complete. A server without continuations requires the legacy fallback of starting a direct query with the same conditions; disclose that extra first-page read. Unordered results are not necessarily the latest. An `inspectionDate` order may require an index and excludes documents lacking that field, so disclose that limitation rather than implying complete history.

For a question needing connected lookups, the agent interprets the question using the catalog and submits a JSON plan to `tms plan` on stdin. This command executes the plan; it is not an LLM and does not interpret natural language itself. Each step has `id`, `query` (same shape as `tms query`, excluding cursor), and optional `retain` with `field`, `op` (`eq` or `part`) and `value`. A filter value may be `{ "refs": [{ "step": "earlier", "field": "orderNumber" }] }`; refs read projected fields from earlier steps. Use `in` for multiple scalar values or `array_any` for a supported array field. The `part` retain comparison removes parenthesized suffixes, so it is only a candidate filter: check product, part, company and specification before treating records as equivalent. Up to 8 steps, 160 total declared document limits, and 3 concurrent queries are permitted; a failed dependency is not treated as an empty finding. Inspect each step's `stats`, `failures`, `limitations`, `searchIncomplete` and sources. Follow up with other permitted queries when needed; exact quality order matching may miss concatenated order numbers. Availability depends on the current server authorization and protected rules release. Never work around a denied or unavailable service with direct Firebase access.

For example, after interpreting a date in Asia/Seoul and checking the catalog, an agent can send the following plan; the second query receives the first step's order numbers without a second round trip from the agent:

```json
{"steps":[{"id":"schedule","query":{"source":"coating-schedule","filters":[{"field":"date","op":"eq","value":"2099-01-01"}],"limit":20}},{"id":"orders","query":{"source":"hwaseong-coating-orders","filters":[{"field":"orderNo","op":"in","value":{"refs":[{"step":"schedule","field":"orderNo"}]}}],"limit":20}}]}
```

1. Interpret the user's question and conversation context. Identify relevant dates, order numbers, product or company names, and whether the answer needs multiple sources. The user does not need to name a collection or command.
2. Convert relative dates using the user's business timezone, defaulting to Asia/Seoul when no other timezone is specified. Distinguish planned schedules from completed production, actual inbound transactions from projected stock, and canceled or pending records from completed events.
3. Use `tms catalog` to discover allowed sources and query fields. Submit bounded `tms query` or `tms plan` requests. The `prefix` operator matches only a literal beginning, including case and spaces; it does not perform a substring search. Check spelling variants explicitly and disclose limitations.
4. Inspect returned `details`, source, document ID, query scope, `possiblyMore` and `nextCursor`. Follow pages when completeness matters. A denied or failed query is not an empty result.
5. For image results use `tms image --inspection ID --index N --output PATH`; image retrieval remains subject to authorization. Never print download-token URLs.

State meaningful limitations and the relevant source and date in the answer. If a field is absent, label it as unrecorded. If a query fails or permissions deny access, say so rather than claiming no records exist. Preserve user's confidential data and never print authentication tokens.

Policy documents are watched and shared on the server, with a direct check after at most 15 seconds. Watch delivery can be delayed; permission revocation is not an atomic instant guarantee. Watch errors discard old values. Rules-release checks are shared for at most 5 seconds. The CLI reuses an unexpired ID token from its OS credential store; server authentication and revocation checks still run per request. `detailsRedacted` or a positive `omittedFields` indicates hidden values, not absent records. `authorizationDocumentsReturned` counts linked ownership checks separately from source documents; neither count includes policy-document/Auth checks or proves billing.
