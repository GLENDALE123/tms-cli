# Agent integration guide

The independent service is deployed for a limited rollout. Indexed search requires `tms retrieve capabilities` to succeed; the index is not yet ready. Direct field queries may be available independently: check `tms catalog` and `query.available`. Employee and partner access depends on verified policies and rollout status. Do not fall back to raw Firebase, Storage URLs, credentials, or disabled legacy commands to bypass an authorization failure.

## Intent and retrieval

Call `tms catalog` to discover business sources, field meanings, relationships and cautions before planning unfamiliar queries. It is manually maintained, not an exhaustive or automatically updated picture of the live database. Confirm uncertain links against evidence, and do not assume historical packaging is the current instruction. The catalog works only after the reviewed service is deployed.

You may create a reusable local criterion with `tms criteria save NAME`, sending `{"kind":"query","request":...}` or `{"kind":"plan","request":...}` as JSON on stdin. Replace a changing value with `{"$param":"name"}`. Use `tms criteria show NAME` to inspect its parameters and send an object with those values to `tms criteria run NAME`. The saved file contains only local query instructions, not a grant of access; the server still validates every source, field, row, user and limit at execution. Local criteria are not automatically shared with other people or devices. Never store passwords, access tokens or secrets in a criterion.

Where a verified non-admin field query is available, a source's `queryScope` describes its current scope. For `mode: own`, add an `eq` condition on the specified company `field` using one of its permitted exact `values`; use additional bounded queries for other listed spellings when necessary. Do not combine names across companies. A source marked unavailable cannot be accessed through field queries even if another search mode supports it. Scope values and permissions may change; fetch the catalog again after a denial or policy change.

An `eq` reference must resolve to exactly one value. If several schedule rows have different suppliers, products or parts, issue separate bounded plans or direct queries for each verified combination; the current plan executor does not perform a row-correlated join automatically. Do not turn the separate lists into independent `in` filters, which can combine keys from unrelated rows.

For paint or process data, the `packaging-reports` field `processConditions` is returned only by an authorized administrator's direct query or plan, not by indexed search. Its `undercoat`, `midcoat`, and `topcoat` contain `conditions` and `remarks`; match the recorded order, part, supplier, specification, work date, and line. Previous production conditions are historical evidence, not a current recipe or instruction. The nested object is not a direct query filter; select reports by supported fields such as `orderNumbers`.

For a used jig, select `quality-inspections` by the supplier, product name and part name together; compare specification as an additional condition when needed. The schedule's `client` corresponds to the inspection's `supplier`. Inspect `inspectionType`, `inspectionDate`, `jigUsed1` (fallback `jigUsed`), `jigUsed2`, and internal jig fields in the approved admin query result; present matching past inspection records with their dates and specifications. Distinguish this history from a jig written on a future schedule. Never merge independent lists of suppliers, products and parts across schedules into a cross-product and assume the returned row belongs to each schedule. Exact Firestore equality is sensitive to differing names, spaces and parenthesized details; a zero result is not proof no history exists. If broader matching is needed, use bounded indexed search or more queries and explicitly verify the full combination; report partial results and index errors rather than silently guessing.

If `possiblyMore` is true, the plan result is only a partial page and currently provides no continuation cursor. When completeness matters, use an individual `tms query` with the same conditions and follow its `nextCursor` in bounded pages; the initial plan page itself is not a cursor. Unordered results are not necessarily the latest. An `inspectionDate` order may require an index and excludes documents lacking that field, so disclose that limitation rather than implying complete history.

For a question needing connected lookups, the agent interprets the question using the catalog and submits a JSON plan to `tms plan` on stdin. This command executes the plan; it is not an LLM and does not interpret natural language itself. Each step has `id`, `query` (same shape as `tms query`, excluding cursor), and optional `retain` with `field`, `op` (`eq` or `part`) and `value`. A filter value may be `{ "refs": [{ "step": "earlier", "field": "orderNumber" }] }`; refs read projected fields from earlier steps. Use `in` for multiple scalar values or `array_any` for a supported array field. The `part` retain comparison removes parenthesized suffixes, so it is only a candidate filter: check product, part, company and specification before treating records as equivalent. Up to 8 steps, 160 total declared document limits, and 3 concurrent queries are permitted; a failed dependency is not treated as an empty finding. Inspect each step's `stats`, `failures`, `limitations`, `searchIncomplete` and sources. Follow up with other permitted queries when needed; exact quality order matching may miss concatenated order numbers. Availability depends on the current server authorization and protected rules release. Never work around a denied or unavailable service with direct Firebase access.

For example, after interpreting a date in Asia/Seoul and checking the catalog, an agent can send the following plan; the second query receives the first step's order numbers without a second round trip from the agent:

```json
{"steps":[{"id":"schedule","query":{"source":"production-schedules","filters":[{"field":"planDate","op":"eq","value":"2099-01-01"}],"limit":20}},{"id":"orders","query":{"source":"hwaseong-coating-orders","filters":[{"field":"orderNo","op":"in","value":{"refs":[{"step":"schedule","field":"orderNumber"}]}}],"limit":20}}]}
```

1. Interpret the user's question and conversation context. Identify relevant dates, order numbers, product or company names, and whether the answer needs multiple sources. The user does not need to name a collection or command.
2. Convert relative dates using the user's business timezone, defaulting to Asia/Seoul when no other timezone is specified. Distinguish planned schedules from completed production, actual inbound transactions from projected stock, and canceled or pending records from completed events.
3. Call `tms retrieve capabilities` to discover indexed sources. `textFields` and `orderFields` describe searchable inputs; `resultFields` describes available evidence, and each source's `note` explains important distinctions. Do not assume a source is indexed merely because TMS has a corresponding screen.
   When `structuredQuery` is true, `querySources` also advertises approved fields for `tms query`; these sources need not already be in the separate search index. Use a server-side `eq`, range, `prefix`, or `prefix_any` filter when it can answer the question without discarding needed variants. Prefix queries match the literal beginning, including case and whitespace; `prefix_any` accepts up to four prefix variants. For substring, spelling variations or uncertain names, use the separate search index or make additional bounded queries; do not claim completeness based on one prefix. Prefer the plan that retrieves fewer documents while preserving evidence. Direct field querying is currently admin-only and disabled until the service is deployed.
4. Send a single structured JSON request on stdin to `tms retrieve`. `terms` is an array of substrings that must all match within a document; it may be empty when `order` or both `from` and `to` are supplied. Optional `sources`, `order`, `from`, `to`, `limit` and `cursor` narrow the search. An order without a suffix matches its base; an order with a suffix is exact. Choose source filters only when helpful; searching across indexed sources can answer cross-domain questions.
5. Inspect result `details`, `source`, document ID, business date, `indexedAt`, `searchIncomplete` and `nextCursor`. A returned hit is an indexed candidate that was checked against the current source version. Search can still miss newer or malformed source records: an empty result, an omitted source, or an error is not proof that an event did not occur. A cursor expires on index changes or service restart; then start the query again. Follow pages only when needed and keep calls bounded.
6. Matching is document-level. If a document contains multiple lines, terms and order number can match different lines. Check the returned lines before attributing a quantity or outcome to a specific item. Do not sum incomplete pages or mix stock snapshots with actual transaction quantities without labeling the distinction.
7. When quality results report `details.imageCount`, use `tms retrieve image --inspection ID --index N --output PATH` and an available image-viewing tool if the user requests image inspection. The image command never returns a Firebase download-token URL. The server currently permits only specifically allowlisted, approved administrators; do not claim this is ready for other users.

State meaningful limitations and the relevant source and date in the answer. If a field is absent, label it as unrecorded. If a query fails or permissions deny access, say so rather than claiming no records exist. Preserve user's confidential data and never print authentication tokens.
